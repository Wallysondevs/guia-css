Projeto: Menu Responsivo

O menu é a primeira coisa que o visitante procura, e o lugar onde o design responsivo mais aparece: no computador, os links cabem lado a lado no topo; no celular, não cabem, e o menu vira uma lista que abre com um botão. Neste projeto você vai construir o menu da lojinha da Ana começando pelo celular (mobile first), em seis versões, e conferir cada uma no quadro com a largura de um celular ou de um tablet.

Você vai usar
  • Listas sem marcador e links com área de toque grande (aula Estilizando Listas).
  • @media (min-width: …) e o raciocínio mobile first (aulas Media Queries e Mobile First).
  • Flexbox: justify-content: space-between, flex-wrap e flex-basis (aulas justify-content e flex-basis).
  • Seletores de atributo: [aria-current="page"] e [aria-expanded="false"] (aula Seletores de Atributo).
  • O combinador +, "o irmão logo depois" (aula Combinadores).
A largura do quadro

Cada caixa deste projeto abre com uma largura fixa: 375 px (um celular) ou 768 px (um tablet). A página dentro do quadro "enxerga" essa largura, e as media queries reagem a ela. Use os botões 375, 768 e cheia da barra do quadro para trocar e ver o menu mudar. As missões são conferidas na largura com que a caixa abriu.

O menu pronto, a versão 6:

O menu pronto: no celular (375 px), clique em Menu para abrir e fechar a lista. Depois aperte o botão 768 da barra do quadro: o botão some e os links ficam lado a lado.

Versão 1: o HTML

O cabeçalho (<header class="topo">) tem o nome da loja, que é um link para o início, e um <nav> com uma lista de links. Dois detalhes de HTML que o CSS vai aproveitar:

  • aria-label="Principal" no <nav> dá um nome ao menu para quem usa leitor de tela.
  • aria-current="page" marca o link da página atual. O leitor de tela anuncia "página atual", e o CSS vai usar o mesmo atributo para destacá-lo (versão 4). Uma marca só, para as duas coisas.

Uma linha clarinha separando os links.

Versão 3: telas largas, com @media

A partir de 600 px de largura, há espaço para tudo numa linha: o nome à esquerda, os links à direita. Como o estilo do celular é a base, a media query só acrescenta o que muda em telas largas (min-width, "no mínimo"):

@media (min-width: 600px) { … }
"Quando a janela tiver pelo menos 600 px de largura". O quadro de 375 px não entra; o de 768 px entra.
.topo { display: flex; justify-content: space-between; align-items: center; }
O nome e o <nav> lado a lado; a sobra de espaço vai para o meio, empurrando cada um para uma ponta; e os dois alinhados pelo centro na vertical.
.menu-lista { display: flex; gap: 4px; margin: 0; }
Os links da lista também lado a lado, com 4px entre eles.
.menu-lista a { border-top: none; }
A linha separadora só fazia sentido na lista empilhada.

Missão (versão 3): o quadro está em 768 px. No fim do style.css, escreva a media query (min-width: 600px) com as quatro regras da anatomia. Depois aperte o botão 375 da barra do quadro: o menu volta a ficar empilhado.

Versão 4: a página atual e os estados

O visitante precisa saber onde está e onde vai clicar:

SeletorO que faz
.menu-lista a:hoverUm fundo branco a 15% com o mouse em cima
.menu-lista a:focus-visibleUm contorno amarelo-claro por dentro do link (outline-offset: -3px), para não ser cortado pelas bordas da barra
.menu-lista a[aria-current="page"]O link da página atual em negrito e sublinhado, com o sublinhado 4px abaixo das letras (text-underline-offset)

Por que [aria-current="page"] e não uma classe .ativo? Porque o atributo já tem de estar lá para o leitor de tela. Estilizar pelo atributo garante que o visual e a acessibilidade nunca fiquem desencontrados: se alguém esquecer o atributo, o destaque também some, e o erro aparece.

Versão 5: o botão Menu, no celular

Com quatro links, a lista empilhada ainda cabe. Com oito, ela empurraria o conteúdo para longe. A solução comum é esconder a lista atrás de um botão Menu. O HTML ganha o botão e um arquivo menu.js:

<button class="topo-botao" type="button" aria-expanded="false" aria-controls="menu">Menu</button>
<nav class="topo-menu" id="menu" aria-label="Principal">

const botao = document.querySelector(".topo-botao");

botao.addEventListener("click", () => {
  const aberto = botao.getAttribute("aria-expanded") === "true";
  botao.setAttribute("aria-expanded", String(!aberto));
});
aria-expanded="false"
Diz ao leitor de tela que o botão controla algo que está fechado. Quando abre, vira "true".
aria-controls="menu"
Diz o que o botão controla: o elemento de id="menu".
menu.js
A cada clique, o script troca o aria-expanded de "false" para "true" e vice-versa. Só isso. Ele não esconde nem mostra nada.
.topo-botao[aria-expanded="false"] + .topo-menu { display: none; }
Quem esconde é o CSS: "o .topo-menu que vem logo depois (+) de um botão fechado fica escondido". Quando o script troca o atributo para "true", o seletor deixa de casar e o menu aparece.

Para o botão ficar à direita do nome, o .topo vira flex também no celular, com flex-wrap: wrap, e o .topo-menu ganha flex-basis: 100%: ele ocupa a linha inteira e "quebra" para baixo do nome e do botão.

Missão (versão 5): o quadro está em 375 px e o HTML já tem o botão e o menu.js. No fim do style.css: o .topo em flex com flex-wrap: wrap, justify-content: space-between e align-items: center; o .topo-menu com flex-basis: 100%; o .topo-botao com borda branca de 2px, fundo transparente, letra branca, font: inherit e cursor: pointer; e a regra que esconde o menu quando o botão está fechado. Depois clique no botão para abrir e fechar.

Versão 6: o botão some nas telas largas

A versão 5 tem um problema: aperte o botão 768 da barra do quadro da missão anterior. No tablet, o menu também ficou escondido atrás do botão, apesar de haver espaço de sobra. As regras da versão 5 vieram depois da media query da versão 3 e valem em qualquer largura. A correção é uma segunda media query, no fim do arquivo, que desfaz o que é só do celular:

.topo-botao { display: none; }
Sem botão em telas largas.
.topo-menu { flex-basis: auto; }
O menu volta a ocupar só o espaço dos links, ao lado do nome.
.topo-botao[aria-expanded="false"] + .topo-menu { display: block; }
O mesmo seletor da versão 5, com a mesma especificidade, mas depois no arquivo: vence o empate e mostra o menu, mesmo com o botão (escondido) "fechado".

Missão final (versão 6): o quadro está em 768 px, e o menu sumiu atrás do botão. No fim do style.css, escreva uma nova media query (min-width: 600px) com as três regras da anatomia, sem !important. Depois troque para 375 e confira que o celular continua com o botão.

E sem JavaScript?

Existe um jeito novo de abrir e fechar sem escrever script: o atributo popover do HTML, com <button popovertarget="menu">. Ele é Baseline 2024 no MDN (desde abril de 2024 nas versões atuais dos navegadores principais). Mas o elemento com popover abre por cima da página, numa camada própria, como um balão, e fazer o mesmo elemento virar uma barra comum nas telas largas exige várias regras a mais. Para um menu de site, a versão deste projeto (um script de 5 linhas que só troca um atributo) é a mais simples de entender e de manter.

Quando dá errado

A media query de telas largas vem antes, e perde

É o erro da versão 5, e o mais comum em CSS responsivo. Uma media query não tem prioridade nenhuma: dentro dela, as regras disputam a cascata como as outras. Se a regra do celular vem depois, com a mesma especificidade, ela vence também no computador. Como achar: no F12, a regra da media query aparece riscada, vencida pela de baixo. Como consertar: no mobile first, as media queries min-width vêm depois das regras que elas mudam, em ordem crescente de largura.

O site no celular de verdade aparece minúsculo

No editor e no F12 o menu fica perfeito, mas no celular de verdade a página aparece encolhida, com letras pequeníssimas, e a media query de 600 px vale sempre. Por quê: faltou a meta viewport no <head>. Sem ela, o celular finge ter uma tela de uns 980 px e encolhe a página (aula A Meta Viewport). O validador não reclama da falta dela. Como consertar: <meta name="viewport" content="width=device-width, initial-scale=1">.

O menu não abre: o + não acha o irmão

Se o <nav> não vier logo depois do botão no HTML (por exemplo, com o logo no meio), o seletor .topo-botao[…] + .topo-menu não casa com nada: o menu nunca é escondido no celular, e clicar no botão não muda nada que se veja. O + pega só o irmão imediatamente seguinte. Como consertar: mantenha o botão e o <nav> vizinhos, ou use o ~ ("qualquer irmão depois", aula Combinadores).

Erro de digitação no script

Se o menu.js tiver um erro (um querySelector(".topo-botão") com acento, por exemplo), o botão não faz nada, e o menu fica fechado para sempre no celular. O console do quadro mostra o erro do navegador, algo como Cannot read properties of null. É um bom motivo para o menu começar aberto se o JavaScript falhar: muitos sites só escondem a lista depois que o script roda (por exemplo, pondo o aria-expanded="false" pelo próprio script).

Resumo

  • Mobile first: o estilo sem media query é o do celular (lista empilhada, links em bloco com área de toque grande); @media (min-width: 600px) acrescenta o das telas largas.
  • Telas largas: .topo em flex com space-between; a lista em flex com gap.
  • [aria-current="page"] destaca a página atual com a mesma marca que o leitor de tela usa; :hover e :focus-visible mostram onde o visitante está.
  • O botão Menu: o script só troca o aria-expanded; o CSS esconde com .topo-botao[aria-expanded="false"] + .topo-menu { display: none; }.
  • A ordem importa: a media query que desfaz o que é do celular vem depois das regras do celular.
  • No site de verdade, a meta viewport é obrigatória para as media queries funcionarem no celular.
