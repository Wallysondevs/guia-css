CSS Estilo de Código

O navegador lê CSS todo amontoado numa linha só sem reclamar. Quem não consegue ler é você, daqui a três meses, ou a pessoa que vai mexer no site da Ana. Estilo de código são as combinações de escrita (espaços, linhas, nomes, ordem) que deixam o CSS fácil de ler, de achar e de consertar. Nesta aula você vai conhecer as regras que este guia usa desde a primeira aula e o porquê de cada uma, e ver os erros que só aparecem quando o código está arrumado.

Você vai aprender
  • O formato de uma regra: indentação de 2 espaços, uma declaração por linha, ; sempre.
  • Nomes de classe: minúsculas, com hífen, dizendo o que a coisa é.
  • Uma ordem para as declarações e para as regras no arquivo.
  • Comentários que ajudam, e o comentário que quebra o CSS (//).
  • Pequenos hábitos: cores, zeros, aspas, atalhos.
  • As ferramentas que arrumam e conferem o código sozinhas.

A ideia: a cozinha arrumada

Numa cozinha bagunçada dá para cozinhar: os ingredientes estão lá, em algum lugar. Mas você perde tempo procurando o sal, pega o açúcar no lugar dele e só descobre quando prova. Numa cozinha arrumada, cada coisa tem o seu lugar, e quem chega de fora acha tudo. CSS arrumado é a mesma coisa: o navegador não liga, mas as pessoas ligam, e os erros ficam à vista.

Veja: estas duas regras desenham exatamente a mesma coisa.

<style>
.aviso{background-color:#fff3cd;border:2px solid #e0a800;padding:12px;border-radius:8px;font-family:sans-serif;color:#5c4400}
</style>
<p class="aviso">A lojinha fecha às 18h no sábado.</p>

<style>
.aviso {
  padding: 12px;
  border: 2px solid #e0a800;
  border-radius: 8px;
  background-color: #fff3cd;
  color: #5c4400;
  font-family: sans-serif;
}
</style>
<p class="aviso">A lojinha fecha às 18h no sábado.</p>

Os dois resultados são o mesmo aviso: fundo amarelo-claro, borda dourada e cantos arredondados. A diferença é para quem lê: no segundo, em um segundo você acha a cor da borda; no primeiro, precisa caçar na linha.

1. O formato de uma regra

.cartao-produto {
  padding: 16px;
  border: 1px solid #cccccc;
  border-radius: 8px;
}

.cartao-produto h2 {
  margin-top: 0;
}
.cartao-produto {
O seletor, um espaço, e a chave que abre, na mesma linha.
␣␣padding: 16px;
Cada declaração na sua linha, com 2 espaços de indentação (o recuo da esquerda). Depois dos dois-pontos, um espaço; antes, nenhum.
;
Ponto e vírgula no fim de toda declaração, até da última. O CSS permite omitir o último, mas quem acrescentar uma linha depois dele vai quebrar a regra sem ver (seção Quando dá errado).
}
A chave que fecha, sozinha na linha, alinhada com o começo do seletor.
(linha em branco)
Uma linha vazia entre uma regra e outra, como parágrafos num texto.

Por que cada uma?

RegraO porquê
Uma declaração por linhaVocê acha a propriedade passando o olho na coluna da esquerda. No Git e nas ferramentas de comparação, mudar uma cor mostra uma linha alterada, e não a regra inteira.
Indentação de 2 espaçosMostra o que está dentro de quê. Dentro de um @media, as regras ganham mais 2 espaços, e as declarações delas, mais 2. Use espaços, não tabulação, para o código ficar igual em qualquer editor.
; sempreAcrescentar uma linha nunca quebra a de cima.
Espaço depois de : e antes de {Separa o nome do valor, como numa frase.
@media (min-width: 600px) {
  .cartao-produto {
    display: flex;
    gap: 16px;
  }
}

Uma exceção aceitável: a regra de uma linha

Muitos projetos aceitam regras curtíssimas, com uma declaração, numa linha só:

.oculto { display: none; }
.centro { text-align: center; }

Com duas declarações ou mais, volte para uma por linha. Este guia usa sempre o formato longo, para você se acostumar.

Missão: arrume a regra do preço no estilo desta aula: uma declaração por linha, 2 espaços de indentação, espaço depois dos dois-pontos e ; em todas, inclusive na última. O resultado no quadro não pode mudar.

<link rel="stylesheet" href="style.css">
<p>Bolo de cenoura: <span class="preco">R$ 35,00</span></p>

.preco{color:#e5533d;font-weight:bold;font-size:1.25rem}

.preco {
  color: #e5533d;
  font-weight: bold;
  font-size: 1.25rem;
}

2. Nomes de classe

O nome de uma classe é a etiqueta de um pote na cozinha. A combinação deste guia:

  • minúsculas, sem acento;
  • palavras separadas por hífen: cartao-produto, botao-comprar (o estilo chamado kebab-case, "espetinho", por causa dos pedaços enfiados no palito);
  • o nome diz o que é, não como parece: .aviso, e não .caixa-amarela. Se um dia o aviso ficar azul, o nome continua certo.
EvitePrefiraPor quê
.CartaoProduto, .cartao_produto.cartao-produtoO hífen é o padrão do próprio CSS (font-size, background-color). Maiúsculas importam: .Cartao não pega class="cartao"
.vermelho, .margem-20.erro, .secaoO nome sobrevive às mudanças de aparência
.c1, .box2.receita-destaqueDaqui a três meses, ninguém lembra o que é c1
#titulo { … } para estilo.titulo { … }O ID tem especificidade alta e só pode aparecer uma vez (aula Seletor de ID)

Para projetos maiores, existe um método de nomes inteiro, com __ e --: aula Organizando Classes (BEM).

3. Uma ordem para as declarações

Dentro de uma regra, a ordem das declarações não muda o resultado (a não ser quando a mesma propriedade aparece duas vezes). Mas uma ordem combinada ajuda a achar as coisas. Há duas escolas:

FormaExemploQuando usar
Por grupo: posição → caixa → texto → aparênciaposition, display, width, padding, border, font-size, color, background-color, transitionA mais comum: as propriedades que mudam o layout ficam no alto, e você lê a regra "de fora para dentro"
Alfabéticabackground-color, border, color, paddingEquipes grandes: não há o que discutir, e uma ferramenta pode ordenar sozinha

Qualquer uma serve, desde que o projeto inteiro use a mesma. Este guia usa a ordem por grupo, como no aviso amarelo do começo.

E a ordem das regras no arquivo?

Do geral para o específico, que é também a ordem que a cascata favorece (aula A Cascata):

  1. variáveis (:root) e o reset;
  2. os elementos (body, h1, a);
  3. o layout (cabeçalho, menu, rodapé);
  4. os componentes (.cartao-produto, .botao);
  5. as media queries de cada parte, junto dela ou no fim.

Quando o arquivo fica grande, ele vira vários arquivos: aula Organizando os Arquivos de CSS.

4. Comentários

Comentário em CSS é só /* … */ (aula Comentários). Use para:

/* ===== Cabeçalho ===== */

.cabecalho {
  display: flex;
  /* O menu precisa ficar por cima do banner */
  z-index: 10;
}
  • títulos de seção, para achar as partes de um arquivo comprido;
  • explicar o porquê de algo estranho (o z-index: 10, um número escolhido para corrigir um bug);
  • não para repetir o óbvio: color: red; /* cor vermelha */ só ocupa espaço.

HábitoExemploPor quê
Hexadecimal em minúsculas, sempre do mesmo jeito#e5533d, e não #E5533D numa linha e #e5533d na outraA busca (Ctrl+F) acha todas as ocorrências

Experimente: esta regra funciona, mas tem cinco hábitos para arrumar: as cores em maiúsculas, o zero com unidade, as aspas simples, o atalho background usado só para a cor e a falta do último ;. Arrume um por um e confira que o resultado não muda.

<link rel="stylesheet" href="style.css">
<h1 class="titulo">Receitas da Ana</h1>

.titulo {
  margin: 0px;
  padding: 12px;
  background: #FFF3CD;
  color: #5C4400;
  font-family: 'Georgia', serif
}

6. Ferramentas que arrumam sozinhas

Ninguém precisa contar espaços à mão. Dois tipos de ferramenta fazem isso pelos programadores:

TipoExemploO que faz
FormatadorPrettier; o "Formatar documento" do VS CodeReescreve o arquivo no formato combinado: indentação, uma declaração por linha, espaços. Não muda o que o CSS faz.
Linter ("verificador")StylelintLê o CSS e aponta problemas: propriedade desconhecida, cor repetida, seletor duplicado, !important. Cada projeto escolhe as regras.
Validadorvnu --css, o validador de CSS do W3CConfere se o CSS segue a especificação. Não olha o estilo, só a correção.

Num projeto com várias pessoas, o formatador roda ao salvar o arquivo, e ninguém discute espaços. Mesmo sem ferramenta, a regra mais importante é a consistência: um estilo meio esquisito usado em todo o arquivo é melhor que três estilos bonitos misturados.

Quando dá errado

Os erros abaixo não são "feios": eles quebram o CSS. E todos ficam muito mais fáceis de ver num código arrumado.

Faltou o ;: duas declarações se perdem 
h1 {
  padding: 8px
  background-color: gold;
}

O que o leitor vê: o título fica sem o preenchimento e sem o fundo dourado. Conferido no Chromium: padding-top calculado 0px e background-color rgba(0, 0, 0, 0) (transparente).

Por quê: sem o ;, o navegador lê uma declaração só: padding: 8px background-color: gold. Esse valor não existe, e a declaração inteira é ignorada. Era a "última" linha que alguém achou que não precisava de ;, até outra pessoa acrescentar uma linha embaixo.

$ vnu --css style.css
"file:/home/ana/site/style.css":3.3-3.18: error: CSS: “padding”: Missing a semicolon before the property name “background-color”.

"Em padding: falta um ponto e vírgula antes do nome de propriedade background-color". O validador aponta a linha 3, onde começa a propriedade que ficou "grudada". Como consertar: ; no fim de toda declaração.

Comentário com //: a regra de baixo some 
// Título da página
h1 {
  color: navy;
}
p {
  color: gray;
}

O que o leitor vê: o título fica preto, não navy; o parágrafo fica cinza normalmente. Conferido no Chromium: h1 com cor calculada rgb(0, 0, 0), p com rgb(128, 128, 128).

Por quê: // é comentário em JavaScript e em outras linguagens, não em CSS. O navegador lê // Título da página h1 como um seletor (inválido) e joga fora a regra inteira, até o }. A regra seguinte escapa.

$ vnu --css style.css
"file:/home/ana/site/style.css":4.2-4.2: error: CSS: Parse Error.

Um "erro de leitura" apontando para o fim da regra quebrada (linha 4). Como consertar: /* Título da página */.

Maiúscula no nome da classe: a regra não pega 
<style>
.Cartao {
  border: 2px solid tomato;
  padding: 8px;
}
</style>
<div class="cartao">Bolo de cenoura</div>

O que o leitor vê: o texto aparece sem borda e sem preenchimento. Por quê: nomes de classe diferenciam maiúsculas de minúsculas: .Cartao e cartao são etiquetas diferentes. O validador não acusa nada, porque os dois nomes são válidos. (Numa página sem <!DOCTYPE html>, o "modo quirks" ignora essa diferença, e o erro aparece só quando alguém acerta o DOCTYPE. Mais um motivo para usar sempre minúsculas.) Como consertar: tudo em minúsculas, no HTML e no CSS.

Resumo

  • O navegador não liga para espaços e linhas; as pessoas ligam. Código arrumado deixa os erros à vista.
  • Formato: seletor e { na mesma linha, uma declaração por linha com 2 espaços, ; em todas, } sozinha, linha em branco entre regras.
  • Classes em minúsculas, com hífen, dizendo o que a coisa é (.cartao-produto, .aviso). Maiúscula conta: .Cartao não pega class="cartao".
  • Declarações numa ordem combinada (por grupo ou alfabética); regras do geral para o específico.
  • Comentários só com /* */: o // faz o navegador jogar fora a regra seguinte (Parse Error).
  • Sem o ;, duas declarações se perdem (Missing a semicolon before the property name).
  • Formatador (Prettier) e linter (Stylelint) fazem e conferem isso sozinhos. O mais importante é a consistência.
