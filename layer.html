CSS Camadas da Cascata

O CSS da lojinha da Ana cresceu: um reset, os estilos básicos de links e títulos, os componentes (botão, cartão, menu) e uns ajustes de última hora. E começou a briga: o botão não fica vermelho porque uma regra antiga, nav a, é mais específica. A saída de sempre seria um !important, ou um seletor ainda mais comprido. O @layer ("camada") resolve de outro jeito: você separa o CSS em camadas e diz a ordem delas. A camada de cima vence a de baixo, seja qual for a especificidade.

Você vai aprender
  • A ideia: grupos de regras com uma ordem de prioridade que você decide.
  • Como criar camadas com @layer nome { } e definir a ordem com @layer a, b, c;.
  • Onde as camadas entram na cascata: antes da especificidade.
  • A surpresa: o CSS fora de qualquer camada vence todas elas.
  • O !important nas camadas, que funciona ao contrário.
  • Camadas aninhadas, camadas sem nome e @import … layer().
  • Os erros mais comuns e as mensagens reais do validador.

Antes, é preciso ter visto A Cascata: Quem Vence e Especificidade; ajuda ter visto !important. Os resultados são desenhados agora pelo seu navegador, e as mensagens do validador saíram do validador W3C (vnu) na máquina fictícia da Ana (usuária ana, computador notebook).

A ideia: a pilha de folhas na mesa

Imagine o CSS como folhas transparentes empilhadas numa mesa. Cada folha é uma camada, e cada uma pinta algumas coisas da página. Olhando de cima, você vê o que a folha de cima pintou; as de baixo só aparecem onde as de cima não pintaram nada. Não importa se a folha de baixo pintou com uma caneta mais grossa (a especificidade maior): quem está em cima cobre.

Sem camadas, todo o CSS fica numa folha só, e a briga é decidida pela especificidade e pela ordem no arquivo. Com @layer, você separa o CSS em folhas (reset, base, componentes…) e escolhe a ordem da pilha. A especificidade só desempata dentro da mesma folha.

1. A primeira camada

O problema da Ana: se a regra antiga do menu fosse só nav a (dois elementos), a classe .botao ganharia dela. Mas a regra era nav#menu a, com um ID, e contra um ID a classe perde. Com camadas, quem decide é a ordem delas:

<style>
  @layer base {
    nav#menu a {
      color: navy;
      background-color: lightgray;
      padding: 8px 16px;
      text-decoration: none;
    }
  }

  @layer componentes {
    .botao {
      color: white;
      background-color: firebrick;
    }
  }
</style>
<nav id="menu">
  <a href="#">Bolos</a>
  <a class="botao" href="#">Encomendar</a>
</nav>

"Bolos" é um link azul-marinho com fundo cinza-claro. "Encomendar" tem o mesmo espaço interno e não tem sublinhado (isso veio da camada base), mas o texto é branco e o fundo é firebrick: as cores vieram da camada componentes, mesmo com a regra nav#menu a, com ID, sendo muito mais específica que .botao.

@layer
Uma regra @ ("at-rule"), como a @media: começa com arroba e envolve outras regras. Layer = "camada".
base
O nome da camada. Você escolhe, como um nome de classe: minúsculas, com hífen se precisar.
{ … }
As regras que moram nessa camada: seletores e declarações normais.
a ordem
A camada que aparece primeiro no CSS fica embaixo na pilha; a que aparece depois fica em cima e vence. Aqui, base e depois componentes.

Repare: a camada não "apaga" a outra. O .botao só disse a cor do texto e a do fundo; o padding e o text-decoration da camada base continuam valendo, porque ninguém em cima falou deles. É igual à cascata de sempre: a disputa é por propriedade.

2. A ordem numa linha só: @layer a, b, c;

Num arquivo grande, a ordem "pela primeira aparição" fica difícil de enxergar. Por isso o costume é declarar a ordem no começo do CSS, numa linha só, sem chaves:

@layer reset, base, componentes;

@layer componentes {
  .botao {
    background-color: firebrick;
  }
}

@layer reset {
  * {
    margin: 0;
  }
}

@layer base {
  a {
    color: navy;
  }
}
@layer reset, base, componentes;
A declaração da ordem: os nomes, separados por vírgula, de baixo para cima na pilha. Termina com ;, sem chaves. Daqui em diante, componentes vence base, que vence reset.
@layer componentes { … } (antes dos outros)
Depois da linha da ordem, os blocos podem vir em qualquer sequência no arquivo, e uma camada pode ganhar regras em vários blocos: tudo é somado na camada, e a ordem da pilha não muda.

Missão: o botão deveria ficar firebrick, mas a camada base está ganhando. Sem mexer nos seletores nem nos blocos, mude só a linha da ordem.

<link rel="stylesheet" href="style.css">
<main>
  <button class="botao" type="button">Encomendar bolo</button>
</main>

@layer componentes, base;

@layer base {
  main button {
    background-color: lightgray;
    padding: 8px 16px;
  }
}

@layer componentes {
  .botao {
    background-color: firebrick;
    color: white;
  }
}

@layer base, componentes;

@layer base {
  main button {
    background-color: lightgray;
    padding: 8px 16px;
  }
}

@layer componentes {
  .botao {
    background-color: firebrick;
    color: white;
  }
}

3. Onde as camadas entram na cascata

Na aula A Cascata, o navegador decide quem vence olhando, em ordem: a importância (!important), a especificidade e a ordem no código. As camadas entram antes da especificidade:

  1. Importância: uma declaração com !important vence uma sem.
  2. Camada: entre declarações normais, a da camada mais alta na pilha vence. E o CSS sem camada fica acima de todas as camadas.
  3. Especificidade: só desempata dentro da mesma camada.
  4. Ordem no código: o último desempate.

A surpresa: o CSS sem camada vence

Uma regra escrita fora de qualquer @layer fica numa "camada invisível" no topo da pilha. Ela vence as regras de todas as camadas, mesmo com especificidade menor, e mesmo escrita antes delas:

<style>
  p {
    color: firebrick;
  }

  @layer base {
    #aviso.destaque {
      color: navy;
    }
  }
</style>
<p id="aviso" class="destaque">Encomendas até sexta-feira.</p>

O texto ficou firebrick. A regra #aviso.destaque tem um ID e uma classe, e veio depois; mas está numa camada, e o simples p, fora de camada, está acima dela.

Isso parece estranho, mas é de propósito: você pode pôr o CSS de outra pessoa (um framework, um tema baixado) numa camada, e o seu CSS, sem camada, vence o dele sem precisar de seletores compridos. A ordem completa, de quem perde para quem vence:

Posição na pilha (declarações normais)Exemplo
1 (perde de todos)a primeira camada: reset
2base
3componentes
4 (vence todos)o CSS sem camada

4. O !important ao contrário

Com !important, a pilha se inverte: um !important na camada mais baixa vence um !important numa camada mais alta, e vence também um !important fora de camada.

<style>
  @layer reset, componentes;

  @layer reset {
    .aviso {
      color: navy !important;
    }
  }

  .aviso {
    color: firebrick !important;
  }
</style>
<p class="aviso">Loja fechada no feriado.</p>

O texto ficou navy: o !important da camada reset, a mais baixa, ganhou do !important sem camada.

Por que assim? A camada de baixo costuma ser a "fundação" (um reset, as regras de acessibilidade). Quando ela diz "isto é importante", é para valer: nenhuma camada de cima pode desfazer. Na prática, o recado é o mesmo da aula !important: com camadas, você quase nunca precisa dele. Se for usar, use só nas camadas de baixo e com motivo.

5. Camadas sem nome, aninhadas e no @import

Camada sem nome

@layer {
  p {
    color: gray;
  }
}

Funciona como uma camada com nome, na posição em que aparece. Mas, como não tem nome, ninguém consegue acrescentar regras nela depois, nem citá-la na linha da ordem. Prefira dar nome.

Camadas dentro de camadas

@layer componentes {
  @layer botoes {
    .botao {
      background-color: firebrick;
    }
  }
}

@layer componentes.botoes {
  .botao {
    color: white;
  }
}

A camada botoes mora dentro de componentes. Para chegar nela de fora, use o ponto: componentes.botoes. É útil em projetos grandes; num site pequeno, uma pilha de três ou quatro camadas basta.

Um arquivo inteiro numa camada

@import url("reset.css") layer(reset);
@import url("tema-baixado.css") layer(tema);

@layer reset, tema, componentes;

O @import (que traz outro arquivo de CSS) aceita layer(nome): todo o arquivo importado entra naquela camada. É o jeito de "domar" um CSS que você não escreveu. Os @import precisam vir no começo do arquivo, antes de qualquer outra regra (só a linha @layer …; pode vir antes deles).

Suporte: o @layer funciona em todos os navegadores atuais desde março de 2022 (o MDN o marca como Baseline: amplamente disponível): Chrome e Edge 99, Firefox 97, Safari 15.4. Um navegador mais antigo não entende a regra @layer e ignora o bloco inteiro, com todas as regras de dentro. O validador W3C (vnu 26.10.12) já conhece o @layer e não acusa as formas certas.

6. Uma organização que funciona

Uma pilha comum, de baixo para cima:

CamadaO que vai nelaExemplo
resetzerar as diferenças entre navegadores (aula Reset e Normalize)* { margin: 0; box-sizing: border-box; }
baseo visual dos elementos soltos: corpo, títulos, links, listasa { color: navy; }
layoutas grandes áreas: cabeçalho, colunas, rodapé.pagina { display: grid; }
componentesas peças: botão, cartão, menu.botao { … }
utilitariosclasses de um efeito só, que devem vencer tudo.escondido { display: none; }

Com essa ordem escrita na primeira linha (@layer reset, base, layout, componentes, utilitarios;), cada regra fica com o seletor mais simples possível, e quem vence fica previsível. A aula Organizando os Arquivos de CSS mostra como dividir isso em arquivos.

Formas diferentes de ganhar uma briga de estilos

Quando dá errado

Com @layer, um erro de escrita costuma apagar um bloco inteiro de regras, e um erro de ordem faz a regra "certa" perder sem aviso.

error: CSS: Unrecognized at-rule “@layers”

O que aconteceu: @layers base { … }, no plural.

$ vnu --css layers.css
"file:/home/ana/camadas/layers.css":1.1-1.7: error: CSS: Unrecognized at-rule “@layers”

"Regra @ não reconhecida: @layers." O navegador também não a conhece e joga fora o bloco inteiro: todas as regras de dentro somem.

Como consertar: @layer, no singular, mesmo na linha que lista várias camadas.

error: CSS: Parse Error. — faltou o ; na linha da ordem

O que aconteceu: a linha @layer base, componentes ficou sem o ;:

<style>
  @layer base, componentes

  @layer base {
    a {
      color: navy;
      text-decoration: none;
    }
  }
</style>
<a href="#">Ver os bolos</a>

O link voltou ao azul e ao sublinhado padrão do navegador: a camada base sumiu inteira. Sem o ;, o navegador leu @layer base, componentes @layer base { … } como uma regra só, com um nome sem sentido, e jogou fora o bloco.

$ vnu --css sem-pv.css
"file:/home/ana/camadas/sem-pv.css":7.2-8.1: error: CSS: Parse Error.

"Erro de leitura." Repare que a posição aponta para o fim do bloco (linhas 7 e 8), e não para a linha 1, onde está o erro: o validador só percebe o problema quando o bloco termina.

Como consertar: @layer base, componentes;. A linha da ordem sempre termina com ;.

error: CSS: Parse Error. — faltou a vírgula

O que aconteceu: @layer base componentes;, os nomes separados só por espaço.

$ vnu --css sem-virgula.css
"file:/home/ana/camadas/sem-virgula.css":1.25-2.1: error: CSS: Parse Error.

A linha da ordem é ignorada, e as camadas ficam na ordem em que os blocos aparecem no arquivo, que pode não ser a que você queria.

Como consertar: @layer base, componentes;, com vírgula.

Pus tudo em camadas, e uma regra velha continua vencendo

O que aconteceu: a Ana organizou o CSS em camadas, mas sobrou, no fim do arquivo, um a { color: purple; } fora de qualquer @layer. Ele vence todas as camadas (seção 3), e os botões, que são links, ficaram roxos. O validador não reclama: não há erro.

Como consertar: no F12, clique no elemento e olhe o painel Styles (Estilos): a regra vencedora aparece no topo. Os navegadores atuais mostram, junto das regras que estão numa camada, o nome dela (ilustrativo: o texto exato muda de navegador para navegador); a regra sem esse nome é a que está fora. Mova-a para a camada certa.

A linha da ordem veio depois

O que aconteceu: o arquivo começa com @layer componentes { … } e só depois tem @layer base, componentes;. A ordem já foi decidida na primeira vez que cada nome apareceu: componentes ficou primeiro (embaixo), e a linha de baixo só acrescentou base depois dela, em cima. A camada base passou a vencer.

Como consertar: a linha da ordem é sempre a primeira do arquivo (depois dela, só os @import).

Referência rápida

CódigoO que faz

Resumo

  • @layer separa o CSS em camadas, como folhas empilhadas: entre declarações normais, a camada de cima vence a de baixo, seja qual for a especificidade.
  • A ordem vem da primeira aparição de cada nome; escreva-a na primeira linha: @layer reset, base, componentes; (de baixo para cima, com vírgulas e ;).
  • Na cascata, as camadas vêm antes da especificidade. A especificidade só desempata dentro da mesma camada.
  • CSS fora de camada vence todas as camadas. Com !important, a ordem se inverte: o da camada mais baixa vence.
  • Camadas sem nome (@layer { }), aninhadas (a.b) e arquivos inteiros com @import … layer(nome).
  • @layers (plural) ou um ; esquecido na linha da ordem apagam blocos inteiros. Baseline desde março de 2022 (Chrome/Edge 99, Firefox 97, Safari 15.4).
