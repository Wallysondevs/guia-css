CSS Rápido

Um site lento perde visitantes: quem abre a lojinha da Ana no celular, com a internet do ônibus, desiste se a tela fica branca por vários segundos ou se a página pula bem na hora do toque. O CSS tem um papel grande nisso, porque o navegador espera o CSS chegar antes de desenhar qualquer coisa. Nesta aula você vai ver o que deixa o CSS lento e os poucos hábitos que o deixam rápido.

Você vai aprender
  • Por que o CSS "segura" o desenho da página, e por que ele vai no <head>.
  • Por que vários <link> são melhores que @import.
  • Arquivos menores: minificar e tirar o CSS que ninguém usa.
  • Fontes da internet sem tela vazia: font-display: swap.
  • Animações leves com transform e opacity.
  • Imagens que não fazem a página pular: aspect-ratio, width e height.
  • content-visibility e will-change: quando ajudam e quando atrapalham.

A ideia: o cozinheiro que lê a receita inteira

Um cozinheiro cuidadoso lê a receita toda antes de começar. Se ele começasse a montar o bolo e só depois descobrisse que a massa leva fermento, teria de desmanchar tudo. O navegador faz o mesmo com o CSS: ele não desenha a página antes de ter o CSS na mão, senão mostraria a página "pelada" (texto preto, fundo branco, tudo empilhado) e depois a redesenharia de repente. Esse "flash" de página sem estilo tem até nome em inglês: FOUC, flash of unstyled content.

Por isso o CSS é chamado de recurso que bloqueia a renderização (render-blocking): enquanto o style.css não chega, a tela fica em branco. Daí vem a regra de ouro desta aula:

CSS rápido = chegar cedo, ser pequeno, dar pouco trabalho

Chegar cedo: o <link> no <head>, sem cadeias de arquivos. Ser pequeno: sem regras que ninguém usa. Dar pouco trabalho: animações e imagens que não obrigam o navegador a recalcular a página toda.

1. O <link> no <head>

<!DOCTYPE html>
<html lang="pt-BR">
<head>
  <meta charset="utf-8">
  <title>Lojinha da Ana</title>
  <link rel="stylesheet" href="style.css">
</head>
<body>
  …
</body>
</html>

No <head>, o navegador descobre o style.css logo nas primeiras linhas e já começa a baixá-lo enquanto lê o resto. Um <link> esquecido no fim do <body> é descoberto tarde: o navegador pode desenhar a página sem estilo e depois redesenhá-la, o FOUC que você viu acima (aula Três Jeitos de Usar CSS).

2. Vários <link> em vez de @import

O CSS tem a regra-at @import, que puxa um arquivo de dentro do outro:

@import url("cores.css");

h1 {
  font-family: sans-serif;
}

Funciona, mas cria uma fila: o navegador só descobre que precisa do cores.css depois de baixar e ler o style.css. São duas viagens pela internet, uma depois da outra, e a tela fica em branco durante as duas. Com dois <link> no HTML, o navegador vê os dois arquivos de uma vez e baixa os dois ao mesmo tempo:

<link rel="stylesheet" href="cores.css">
<link rel="stylesheet" href="style.css">
FormaComo o navegador baixaUse?
Um <link> sóUma viagemSim: o melhor para um site pequeno
Vários <link> no <head>Todas as viagens ao mesmo tempoSim, quando você separa os arquivos (aula Organizando os Arquivos)
@import dentro do CSSEm fila: um arquivo, depois o outroEvite no site publicado

A ordem dos <link> continua importando para a cascata: o que vem depois vence os empates (aula A Cascata).

3. Arquivos menores

Minificar: tirar o que só serve para pessoas

Espaços, quebras de linha e comentários ajudam você a ler o CSS, mas o navegador não precisa deles. Minificar é apagar tudo isso (e encurtar o que der, como #ffffff → #fff) numa cópia para publicar. Veja os dois arquivos na pasta da Ana:

$ cat style.min.css
.botao{background-color:#ff6347;color:#fff;padding:12px 24px;border-radius:8px}.botao:hover{background-color:#e5533d}
$ wc -c style.css style.min.css
217 style.css
117 style.min.css
334 total

O wc -c conta os bytes: a mesma regra caiu de 217 para 117 bytes, quase metade. Num arquivo de verdade, com centenas de regras, a economia é parecida. A versão minificada é feita por um programa (os minificadores, que costumam vir junto das ferramentas de publicação de sites), nunca à mão: você continua editando o style.css legível, e o programa gera o style.min.css. Os servidores ainda compactam o arquivo na viagem (gzip ou brotli), o que ajuda muito em arquivos grandes.

Tirar o CSS que ninguém usa

Com o tempo, o style.css junta regras de páginas que não existem mais, classes que ninguém usa e frameworks inteiros dos quais só um botão é aproveitado. Tudo isso é baixado e lido em cada visita. No Chrome, as ferramentas do desenvolvedor (F12) têm um painel de cobertura (Coverage) que pinta de vermelho as linhas do CSS que a página não usou; os nomes exatos do menu mudam de versão para versão. Antes de apagar, lembre que uma regra não usada nesta página pode ser usada em outra.

4. Fontes da internet sem tela vazia

Uma fonte baixada com @font-face (aula Fontes da Internet) é mais um arquivo na fila. Enquanto ela não chega, alguns navegadores deixam o texto invisível por até alguns segundos. O descritor font-display diz o que fazer enquanto isso:

@font-face {
  font-family: "Lato";
  src: url("fontes/lato.woff2") format("woff2");
  font-display: swap;
}
font-displayEnquanto a fonte não chega
swapMostra o texto já, com uma fonte do sistema, e troca ("swap") quando a fonte chega. O mais usado.
optionalSe a fonte não chegar quase na hora, fica a do sistema nesta visita. A página nunca muda depois de aparecer.
blockEsconde o texto por um tempo, esperando a fonte. Evite em textos.
autoO navegador decide (em geral, igual ao block).

Outras economias: use o formato woff2 (o mais compacto) e só os pesos que a página usa. Cada peso (400, 700, itálico…) é um arquivo a mais.

5. Animações leves: transform e opacity

Para desenhar uma página, o navegador faz três trabalhos, nesta ordem:

  1. Layout (organizar): calcula onde fica cada caixa e o tamanho de cada uma. Mudar width, height, margin, top, left ou font-size obriga a refazer isto, e às vezes a página toda.
  2. Pintura: pinta as cores, as bordas, as sombras, o texto. Mudar color, background-color ou box-shadow refaz a pintura.
  3. Composição: junta as camadas já pintadas, como folhas de papel vegetal umas sobre as outras. Mudar transform ou opacity pode ser feito só aqui, deslizando ou clareando uma camada pronta, muitas vezes pela placa de vídeo.

Numa animação, o navegador refaz esse trabalho até 60 vezes por segundo (ou mais, nas telas mais rápidas). Animar left refaz o layout em todas elas; animar transform só mexe na composição. Num computador rápido você não vê diferença; num celular simples, a primeira pode "engasgar".

6. Imagens que não fazem a página pular

Você está lendo uma notícia no celular e, de repente, o texto desce meio palmo: uma imagem acabou de chegar e empurrou tudo. Pior: você ia tocar num link e tocou num anúncio. Isso se chama deslocamento do layout (layout shift), e o Google mede (o "CLS", uma das notas de qualidade de um site).

O motivo: enquanto a imagem não chega, o navegador não sabe a altura dela e reserva zero. A cura é dizer a proporção antes, de um destes jeitos:

FormaExemploQuando usar
width e height no HTML<img src="bolo-800.jpg" alt="…" width="800" height="600"> com img { max-width: 100%; height: auto; } no CSSSempre que você souber o tamanho da imagem: o navegador calcula a proporção sozinho
aspect-ratio no CSS.foto { width: 100%; aspect-ratio: 4 / 3; }Quando todas as fotos de um lugar têm a mesma proporção, ou num vídeo e num iframe (aula Proporção)

Com o aspect-ratio: 4 / 3 e a largura de 100% numa janela de 600 pixels (584 de área útil, descontada a margem do body), o Chromium reserva 438 pixels de altura antes mesmo de a imagem chegar (conferido: altura calculada 438px). O valor calculado de aspect-ratio é 4 / 3.

7. content-visibility: só desenhe o que está na tela

Numa página muito comprida (o blog com 200 receitas), o navegador organiza e pinta tudo, até o que está lá embaixo e ninguém viu. Com content-visibility: auto, ele pula o trabalho das seções que estão longe da tela e só as desenha quando o leitor rola até perto delas:

.receita {
  content-visibility: auto;
  contain-intrinsic-size: auto 500px;
}
content-visibility: auto;
"Visibilidade do conteúdo: automática". Fora da tela, o conteúdo da seção não é organizado nem pintado. O texto continua na página: a busca do navegador (Ctrl+F) e os leitores de tela o encontram.
contain-intrinsic-size: auto 500px;
Um tamanho "de mentirinha" para a seção enquanto ela não é desenhada. Sem ele, a seção pulada mede quase zero, e a barra de rolagem salta quando ela finalmente é desenhada. O auto diz: "depois de desenhar uma vez, lembre o tamanho de verdade".
Suporte

content-visibility é Baseline 2024 no MDN (desde setembro de 2024 nas versões atuais do Chrome, Edge, Firefox e Safari). Num navegador antigo, a propriedade é ignorada e a página só fica como era: é uma melhoria segura. Só vale a pena em páginas longas; numa página curta não muda nada.

8. will-change: um aviso, não um turbo

.carrinho-aberto {
  will-change: transform;
}

will-change ("vai mudar") avisa o navegador de que aquela propriedade vai ser animada logo, para ele se preparar (por exemplo, criando uma camada só para o elemento). Uma camada custa memória. Por isso:

  • use só num elemento que de fato vai ser animado e que mostrou engasgo;
  • nunca em tudo (* { will-change: transform; }): o navegador gasta memória em centenas de camadas e a página fica mais lenta;
  • na dúvida, não use: para a maioria das animações com transform, o navegador já se vira bem sozinho.

9. Um mito: "seletor comprido deixa o site lento"

Você vai ler em textos antigos que .menu ul li a é lento e que seletores devem ser curtos. Os navegadores de hoje casam milhares de seletores em milésimos de segundo; numa página comum, a diferença não se mede. Escolha o seletor que deixa o código claro (aulas Especificidade e BEM) e gaste o esforço de performance nos itens desta aula, que fazem diferença de verdade.

Quando dá errado

@import depois de outra regra: o arquivo nem é baixado 
h1 {
  font-family: sans-serif;
}
@import url("cores.css");

O que o leitor vê: o título continua preto, como se o cores.css (que pinta o h1 de tomato) não existisse. Conferido no Chromium: a cor calculada do h1 fica rgb(0, 0, 0).

Por quê: o @import só vale no começo do arquivo, antes de qualquer regra. Depois de uma regra, o navegador o ignora em silêncio.

$ vnu --css style.css
"file:/home/ana/site/style.css":4.26-5.1: error: CSS: @import are not allowed after any valid statement other than @charset and @import.

"@import não é permitido depois de nenhuma instrução válida, a não ser @charset e @import". Como consertar: melhor ainda que subir o @import para a primeira linha: troque-o por um <link> no HTML.

font-display fora do @font-face 
h1 {
  font-display: swap;
}

O que o leitor vê: nada muda: o texto continua esperando a fonte. Por quê: font-display não é uma propriedade de elementos; é um descritor que só existe dentro do @font-face, junto do src. Fora dele, o navegador ignora a linha.

$ vnu --css style.css
"file:/home/ana/site/style.css":2.17-2.20: error: CSS: “font-display”: Property “font-display” doesn't exist.

"A propriedade font-display não existe" (como propriedade de um elemento). Como consertar: mova a linha para dentro do @font-face da fonte.

O CSS no fim do <body>: o flash de página sem estilo

O que o leitor vê: numa internet lenta, a página aparece por um instante com texto preto em fundo branco, tudo empilhado, e depois "se arruma". Num computador com internet rápida, quase não se nota, e é por isso que o erro passa despercebido. Por quê: o navegador começou a desenhar antes de descobrir o <link>. O validador não reclama: <link rel="stylesheet"> no <body> é permitido. Como consertar: o <link> no <head>.

will-change em tudo: a página ficou mais lenta

* { will-change: transform; } é CSS válido (o validador não reclama), mas cria uma camada para cada elemento da página. Em celulares, isso pode gastar tanta memória que a rolagem engasga. Como consertar: apague a regra; se uma animação específica engasgar, ponha will-change só naquele elemento.

No quadro, a página parece igual antes e depois, e é isso mesmo: performance raramente se vê numa página pequena, num computador rápido. Ela aparece no celular simples, na internet lenta e na página com cem fotos.

Resumo

  • O navegador espera o CSS para desenhar (render-blocking): o <link> vai no <head>, ou a página pisca sem estilo.
  • Vários <link> baixam ao mesmo tempo; @import cria uma fila (e só vale no começo do arquivo: @import are not allowed after any valid statement).
  • Arquivo menor: minificar numa cópia para publicar e tirar as regras que ninguém usa (painel de cobertura do F12).
  • font-display: swap, dentro do @font-face, mostra o texto já; fora dele, Property “font-display” doesn't exist.
  • Anime transform e opacity; evite animar width, margin, top, left.
  • width/height no <img> ou aspect-ratio reservam o espaço e a página não pula.
  • content-visibility: auto ajuda em páginas longas; will-change só onde precisa. Seletor comprido não é problema de velocidade.
