CSS @supports e Compatibilidade

O CSS ganha recursos novos todo ano, mas o site da Ana é aberto em celulares e computadores com navegadores de várias idades. Como usar o recurso novo sem quebrar a página de quem tem um navegador mais velho? O CSS tem duas respostas. A primeira já vem de graça: o navegador ignora o que não entende. A segunda é uma pergunta que você faz ao navegador antes de aplicar as regras: @supports, "você entende isto?".

Você vai aprender
  • A declaração reserva: escrever o valor antigo e, logo depois, o novo.
  • @supports (propriedade: valor) { … }: regras que só valem se o navegador entende a declaração.
  • not, and, or e selector().
  • A mesma pergunta no JavaScript: CSS.supports().
  • Como descobrir se um recurso funciona em todos os navegadores: o Baseline e a tabela do MDN.
  • O que são os prefixos -webkit-, e por que não escrevê-los à mão.
  • O que o @supports não sabe responder, e os erros reais do validador W3C.

Os resultados são desenhados pelo seu navegador. Os valores do estilo calculado foram conferidos no Chromium; as mensagens de erro são do validador W3C (vnu) rodado na máquina fictícia da Ana (ana@notebook), na pasta ~/site.

A ideia: "aceita Pix?"

Na padaria, antes de pagar, você pergunta: "aceita Pix?". Se aceita, você paga com Pix. Se não, paga em dinheiro. Você não chega com o celular na mão e fica parado esperando.

No CSS é igual:

  • A reserva: leve o dinheiro e o Pix. Escreva a declaração antiga e logo depois a nova. Quem entende a nova usa a nova; quem não entende fica com a antiga.
  • A pergunta: @supports pergunta antes, e aplica um bloco inteiro de regras só se a resposta for "sim".

1. A reserva: o navegador ignora o que não entende

Você já viu nas aulas anteriores: uma declaração que o navegador não entende é jogada fora, sem mensagem, e as outras continuam valendo. Isso vira uma ferramenta. Escreva duas vezes a mesma propriedade, a conhecida primeiro e a nova depois:

.botao {
  background-color: tomato;
  background-color: oklch(70% 0.2 30);
}
background-color: tomato;
A reserva: uma cor que todo navegador conhece desde sempre.
background-color: oklch(…);
A cor nova, num formato mais recente (aula Cores Modernas). Pela cascata, a declaração de baixo vence a de cima (aula Cascata).

Um navegador que entende oklch() usa a segunda; no Chromium, o estilo calculado ficou oklch(0.7 0.2 30). Um navegador que não entende joga a segunda fora e fica com tomato. Para conferir o que acontece no navegador antigo, basta estragar o valor novo: com oklch(70% 0.2 30 / zzz), que nenhum navegador entende, o Chromium ficou com rgb(255, 99, 71), o tomato.

A ordem importa

A reserva vem antes. Na ordem contrária, a cor antiga, que todo mundo entende, sempre venceria, e ninguém veria a nova.

Para uma declaração, a reserva resolve. Mas às vezes o recurso novo pede várias mudanças juntas. Um layout com subgrid, por exemplo, precisa de display: grid, grid-row: span 3 e grid-template-rows: subgrid. Se só a última for ignorada, as outras duas ficam lá, e o resultado pode ficar pior que o original. É para isso que existe o @supports.

2. A pergunta: @supports

@supports (display: grid) {
  .galeria {
    display: grid;
    grid-template-columns: repeat(3, 1fr);
    gap: 12px;
  }
}
@supports
"Suporta". Uma regra com arroba, como a @media: ela não estiliza nada sozinha, ela embrulha outras regras.
(display: grid)
A condição: uma declaração inteira, propriedade e valor, entre parênteses e sem o ;. A pergunta é: "você entende display: grid?".
{ … }
As regras de dentro, escritas normalmente. Só valem se a resposta for "sim". Se for "não", o navegador pula o bloco inteiro.

Abaixo, cada linha só fica verde se o seu navegador entende a condição escrita nela. As duas últimas são falsas de propósito: inexistente não é um valor de display, em nenhum navegador.

<style>
  p {
    padding: 6px 10px;
    background-color: #ddd;
    font-family: monospace;
  }
  @supports (display: grid) {
    .t1 { background-color: lightgreen; }
  }
  @supports (grid-template-rows: subgrid) {
    .t2 { background-color: lightgreen; }
  }
  @supports selector(:has(a)) {
    .t3 { background-color: lightgreen; }
  }
  @supports (display: inexistente) {
    .t4 { background-color: lightgreen; }
  }
  @supports (subgrid) {
    .t5 { background-color: lightgreen; }
  }
</style>
<p class="t1">(display: grid)</p>
<p class="t2">(grid-template-rows: subgrid)</p>
<p class="t3">selector(:has(a))</p>
<p class="t4">(display: inexistente)</p>
<p class="t5">(subgrid)</p>

No Chromium, as três primeiras ficaram verdes e as duas últimas, cinza. A última é um erro comum: (subgrid) não é uma declaração, falta a propriedade. A condição precisa ser (propriedade: valor), completa.

Missão: a galeria da Ana é uma lista simples, uma foto embaixo da outra. Dentro de um @supports (display: grid), transforme a .galeria num grid de 2 colunas (grid-template-columns: 1fr 1fr), com gap: 12px. Quem não entende grid continua vendo a lista, que também funciona.

<link rel="stylesheet" href="style.css">
<h1>Galeria</h1>
<div class="galeria">
  <img src="assets/midia/bolo-400.jpg" alt="Bolo de cenoura inteiro" width="400" height="300">
  <img src="assets/midia/bolo-quadrado-400.jpg" alt="Fatia quadrada do bolo" width="400" height="400">
</div>

.galeria img {
  display: block;
  width: 100%;
  height: auto;
  margin-bottom: 12px;
}

.galeria img {
  display: block;
  width: 100%;
  height: auto;
  margin-bottom: 12px;
}

@supports (display: grid) {
  .galeria {
    display: grid;
    grid-template-columns: 1fr 1fr;
    gap: 12px;
  }
}

3. not, and, or e selector()

A condição pode ser combinada, como numa frase:

EscritaVerdade quando…Exemplo de uso
@supports not (A)o navegador não entende AMostrar um aviso, ou um ajuste, só para os navegadores antigos
@supports (A) and (B)entende A e BUm layout que precisa das duas coisas
@supports (A) or (B)entende A ou B (pelo menos uma)Duas formas de escrever a mesma coisa
@supports selector(:has(a))entende o seletor :has(a)Usar um seletor novo (aula :has()) com segurança

Duas regras de escrita:

  • Cada parte entre parênteses, e um espaço antes e depois de and/or/not.
  • Não misture and e or no mesmo nível. (A) and (B) or (C) é ambíguo, e o navegador descarta a regra inteira; no Chromium, o bloco não foi aplicado. Use parênteses para dizer a ordem: ((A) and (B)) or (C), que funcionou.

O selector() pergunta por um seletor, e não por uma declaração. No Chromium, selector(:has(a)) deu "sim", e selector(:inexistente) deu "não".

A mesma pergunta no JavaScript: CSS.supports()

Se um script precisa saber a resposta, ele pergunta ao objeto CSS do navegador:

Experimente: veja as respostas no console, embaixo do quadro. Troque grid por outro valor e veja o true virar false.

<p>Veja o console.</p>
<script>
  console.log(CSS.supports("display", "grid"));
  console.log(CSS.supports("display: inexistente"));
  console.log(CSS.supports("selector(:has(a))"));
</script>

No Chromium, o console mostrou true, false e true. Repare nas duas formas: com dois textos (a propriedade e o valor separados) ou com um texto igual à condição do @supports, sem os parênteses de fora. Para estilo, prefira o @supports no CSS; o JavaScript é para quando o script muda de comportamento.

4. Como saber se um recurso funciona em todo lugar

Antes de usar um recurso, confira a compatibilidade. Os dois lugares de sempre:

OndeO que olhar
MDN (developer.mozilla.org)No topo da página de cada propriedade, o selo Baseline. No fim, a tabela "Compatibilidade com navegadores", com a versão de cada navegador.
caniuse.com ("posso usar?")Busque o nome do recurso: verde é suportado, vermelho não, amarelo é suporte parcial (leia a nota).

O selo Baseline resume a tabela numa frase:

SeloQuer dizerO que fazer
Amplamente disponível (widely available)Funciona nos navegadores principais (Chrome, Edge, Firefox, Safari) há mais de dois anos e meio.Use sem medo.
Recentemente disponível (newly available)Acabou de chegar ao último dos navegadores principais. Quem não atualiza ainda não tem.Use com uma reserva ou dentro de @supports.
Disponibilidade limitada (limited availability)Falta pelo menos um navegador principal.Só como melhoria: a página tem de funcionar sem ele.

Um exemplo real: o subgrid está marcado no MDN como amplamente disponível, em todos os navegadores desde setembro de 2023. O @supports selector() funciona nos três motores principais desde 2021 (Chrome 83, Firefox 69, Safari 14.1, pela tabela do MDN).

Melhoria progressiva

A ideia por trás desta aula tem nome: melhoria progressiva (progressive enhancement). Primeiro, uma página que funciona em qualquer navegador, com o CSS mais simples. Depois, por cima, as melhorias para quem as entende. Ninguém fica com a página quebrada; quem tem o navegador novo ganha um pouco mais.

Os prefixos: -webkit-, -moz-

Em CSS antigo, você vai ver propriedades com um prefixo na frente:

.botao {
  -webkit-appearance: none;
  -moz-appearance: none;
  appearance: none;
}

Por muitos anos, cada navegador lançava os recursos novos com o seu prefixo (-webkit- no Safari e no Chrome, -moz- no Firefox), e os sites escreviam a mesma coisa três vezes. Hoje os recursos saem sem prefixo: o appearance sem prefixo funciona em todos os navegadores principais desde março de 2022 (MDN). Por isso:

  • Reconheça os prefixos quando aparecerem em código antigo ou copiado.
  • Não escreva à mão. Quando um prefixo ainda é necessário, uma ferramenta (como o Autoprefixer) os acrescenta sozinha, consultando a mesma base de dados do caniuse.
  • Se escrever, a versão sem prefixo vem por último, pelo mesmo motivo da reserva.

5. Qual usar

SituaçãoUse
Uma declaração nova com uma alternativa antiga (uma cor, uma unidade)A reserva: a antiga, depois a nova
Várias declarações que só fazem sentido juntas (um layout novo)@supports (…) { … }
Um ajuste só para navegadores antigos@supports not (…) { … }
Um seletor novo (:has())@supports selector(…) { … }
Um script que precisa decidirCSS.supports(…)
Recurso marcado como "amplamente disponível"Nenhum dos dois: use direto

Quando dá errado

Sem parênteses ou com ;: Parse Error 
@supports display: grid {
  .e { color: green; }
}
@supports (display: grid;) {
  .f { color: green; }
}

$ vnu --css estilo.css
"file:/home/ana/site/estilo.css":3.2-3.2: error: CSS: Parse Error.
"file:/home/ana/site/estilo.css":4.25-4.25: error: CSS: “display”: Parse Error.
"file:/home/ana/site/estilo.css":6.2-7.1: error: CSS: “display”: Parse Error.

O que significa: "erro de leitura": o validador não conseguiu entender a regra. A primeira não tem os parênteses em volta da declaração (ele percebe no fim do bloco, na linha 3); a segunda tem um ; dentro deles (a coluna 25 da linha 4 é justamente o ;), e o validador se perde até o fim do bloco (linhas 6 e 7).

O que o leitor vê: nada muda. No Chromium, os dois blocos foram ignorados por inteiro: o .e e o .f continuaram pretos. Uma condição mal escrita é tratada como "não suporta".

Como consertar: @supports (display: grid) {: a declaração entre parênteses, sem ;.

O validador reclama de uma condição not que está certa 
@supports not (display: inexistente) {
  .b { color: green; }
}

$ vnu --css estilo.css
"file:/home/ana/site/estilo.css":1.25-1.35: error: CSS: “display”: “inexistente” is not a “display” value.

O que significa: "inexistente não é um valor de display". O validador confere a declaração de dentro da condição como se fosse uma declaração comum. Mas, num @supports not, testar algo que o navegador não entende é justamente a ideia, e no Chromium a regra funcionou (o .b ficou verde). O mesmo acontece ao testar um recurso que o validador ainda não conhece.

O que fazer: leia a mensagem e decida. Se a declaração da condição está escrita certo e você quer testar algo que pode não existir, o aviso pode ser ignorado. Se foi um erro de digitação (dispaly, gird), conserte. No botão Validar no W3C das caixas do guia, esse erro aparece marcado como Error (falso).

"Suporta" não quer dizer "funciona do jeito que eu quero"

O que acontece: o @supports só pergunta se o navegador entende a declaração. Ele não sabe se ela funciona em todos os casos. O exemplo clássico: por alguns anos, o Safari entendia gap no Grid, mas ainda não no Flexbox (o gap no Flexbox chegou no Safari 14.1, em 2021). @supports (gap: 1rem) respondia "sim", e os itens de um flex ficavam grudados.

O que fazer: confira a compatibilidade do caso que você vai usar no MDN ou no caniuse (o MDN separa, na tabela, linhas como "suporte em layout flex"). E teste no navegador.

A reserva na ordem errada: o recurso novo nunca aparece 
.botao {
  background-color: oklch(70% 0.2 30);
  background-color: tomato;
}

O que o leitor vê: o botão sempre tomato, em qualquer navegador. A última declaração válida vence, e todos entendem tomato. Nenhum validador acusa: as duas declarações estão corretas. Ponha a reserva antes.

}

Resumo

  • O navegador ignora a declaração que não entende. Use isso como reserva: a declaração antiga primeiro, a nova depois.
  • @supports (propriedade: valor) { … } aplica um bloco inteiro só se o navegador entende a declaração. Parênteses obrigatórios, sem ;.
  • not, and, or combinam condições (parênteses para misturar); selector() pergunta por um seletor; CSS.supports() faz a mesma pergunta no JavaScript.
  • "Suporta" quer dizer "entende", e não "funciona em todos os casos". Confira no MDN (selo Baseline) e no caniuse.
  • Prefixos (-webkit-) são coisa do passado: reconheça, não escreva à mão.
  • O validador acusa Parse Error numa condição mal escrita, e às vezes reclama de uma condição certa que testa algo desconhecido.
